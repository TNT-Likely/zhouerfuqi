# i18n(国际化)评估

日期:2026-11-19 · 结论:**现阶段不做,预留架构**

## 一、现状

| 面 | 现状 |
| --- | --- |
| UI 文案 | 全部硬编码中文(约 60+ 处字符串,集中在 8 个屏幕文件) |
| 商店呈现 | Play 商品详情已备 zh-CN;TestFlight 面向中文用户 |
| 目标用户 | 中国轮班/大小周人群(产品语义:大周小周/调休补班/节假日联动 深度绑定中国语境) |
| 引擎 | `@zhouerfuqi/core` 的节假日联动 = holiday-cn(中国法定节假日),无其他国家日历 |

## 二、成本

1. **文案抽取**:8 屏 ~60 处 → react-i18next(或轻量自写 Context 词典),一次性 0.5~1 天;
   此后新增文案双倍维护。
2. **语义难点(不是翻译,是产品语义)**:
   - 「大周 / 小周」是中国制造/班组排班特有的概念,英文无对应词(需译作 big week/small week
     并加解释);「调休补班」同理(make-up workday)。
   - 每周起始日:中国=周一,美国=周日,中东=周六 → 日历组件与「七日节律带」的 WD 常量、
     周环高亮逻辑都要按 locale 配置。
   - **节假日引擎是硬依赖**:holiday-cn 只覆盖中国。若支持海外用户,要么该功能按地区降级
     (纯规则模式),要么接入 Nager.Date 等其他日历源——这是引擎级改造,不是文案级。
3. **日期/数字格式**:date-fns/locale 或 Intl API 适配,工作量小但琐碎。
4. **商店/审核**:每个新语言 = Play 商品详情 + 隐私政策(已双语)+ IARC 问卷再核。

## 三、收益判断

- 当前获客渠道(开源社区 + 朋友圈 + 国内排班人群)**100% 中文**;
- 海外没有「大小周」用工制度,核心场景不存在,自然需求接近零;
- TestFlight/Play 公开链接是中文社区分发的,近期不可能带来规模外语用户。

## 四、建议

**现在不做。** 触发条件(满足任一再启动):
1. GitHub Issues / 应用内反馈出现 ≥5 个非中文用户的真实需求;
2. 计划出海版本(需要先做 holiday 引擎的地区抽象 + 「大小周」概念重审)。

**现在做的一件事(成本≈0)**:新写的 UI 文案集中到少量常量(不散落内联),
将来抽取时用正则即可批量迁移——本次 design v2 改版已遵守(新组件文案集中)。

## 五、若将来启动,推荐架构

- `react-i18next` + `zh-CN.ts` / `en-US.ts` 两词典;命名空间按屏幕切分;
- `dayjs` + locale 做日期格式;周起始日进 locale 配置;
- 节假日引擎抽象 `HolidaySource` 接口:`china-smart`(现状)/ `raw`(普适)/ 未来 `nager:<country>`;
- Play 商品详情按上架语言逐个补(资源在 design/ 与商店后台,代码零改动)。
